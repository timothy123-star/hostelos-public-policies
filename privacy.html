1. Who this policy covers

HostelOS is a digital hostel booking, management and security system. During the controlled pre-launch test, it processes information of volunteer testers acting as prospective residents (students), and of the hostel manager account that reviews bookings, payments, photographs and access credentials.

Use subject HostelOS Data Access or Deletion Request and include your name and registered WhatsApp number. This is a temporary pre-launch contact for testing purposes. It is not Nova Residence’s appointed Data Protection Officer or permanent official contact; those remain to be designated by Nova Residence.

4. WhatsApp / Meta processing

When Meta WhatsApp Cloud API credentials are configured (the current test state), booking messages and photographs you send to the test number are transmitted through WhatsApp and retrieved by HostelOS through Meta’s Cloud API for processing as described above. Meta therefore processes message content as part of delivering the service. Photographs received this way are stored by HostelOS and held for manager review; they are not published.

5. Test infrastructure (Cloudflare tunnel)

During the current test, inbound Meta webhook traffic reaches the test server through a temporary Cloudflare Quick Tunnel that forwards only the /api/whatsapp/webhook path to the application. Other application paths are rejected by the tunnel gateway. The tunnel hostname changes between test sessions and provides no permanent address for the service.

6. Where data is stored (current demo)

The pilot uses an isolated SQLite database file on the test server and a private local photograph directory that is deliberately kept outside any public web directory. Photographs are not served by public URLs; limited single-use upload links, where used, expire automatically. This is a demonstration arrangement, not the architecture for full operational use, which Nova Residence must approve.

7. Access restrictions and security controls actually implemented

  • Manager functions (payment approval, photograph review, credential issuance, relocation) require an authenticated manager session (signed credentials); self-service actions such as photograph upload use single-use expiring links.
  • Resident QR tokens are generated from cryptographic randomness; only a one-way hash is stored, credentials are revocable and re-issuable, and QR issuance requires prior payment verification and photograph approval.
  • Male and female facility data and allocation are kept separate by design, and rooms under maintenance or held by another group cannot be allocated.
  • Manager overrides (for example relocations) require a recorded reason and create an audit-log entry.
  • There is no self-service automated deletion in the current build; access and deletion requests are handled manually as described in section 10 and on the data-deletion page.

8. Payments (demonstration only)

HostelOS is not a payment gateway and has no live bank integration. The “demo bank transfer” and reconciliation screens are synthetic: they simulate a transfer and a ledger entry so the manager-approval workflow can be tested. Payment verification requires explicit manager approval after reconciling the simulated ledger entry; direct self-verification is disabled. No real money moves and no real bank details are processed.

9. Roommate matching and manager approval

Automatic roommate matching may suggest placements (first-in-first-out within eligibility and consent rules), but it only assists allocation: final placement requires verified payments for the group and manager-controlled allocation steps, and QR credentials are issued only after manager authorisation. Payment verification always requires explicit manager approval.

10. Retention and deletion

Booking, allocation and credential records are kept for the accommodation period (including start/end dates and renewals) and for a reasonable period afterwards to handle disputes, audit and any lawful record-keeping obligation. Photograph submissions are retained as a review history including the manager’s decision. To request access, correction or deletion, follow the manual process on the data-deletion page. Where a lawful obligation requires retention (for example audit or financial records), the affected data is retained only to the extent required and is not used for other purposes.

11. Your rights under Nigerian law

Under the Nigeria Data Protection Act 2023 (and regulations/guidance of the Nigeria Data Protection Commission), you have rights including to be informed about processing, to access your personal data, to request correction of inaccurate data, to request deletion where applicable, to withdraw consent where processing relies on it, to object to or request restriction of certain processing, and to lodge a complaint with the Commission. To exercise these rights during the pilot, contact the pilot address in section 2. This section is general information, not legal advice.
